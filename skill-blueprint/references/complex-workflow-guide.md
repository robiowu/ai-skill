# 复杂流程分治设计指南

> 原则 9 的完整落地指南。当被设计 skill 涉及大批量、强流程、且不适合纯脚本固化时，使用 subagent 拆解 + 本地 md 追踪进度。

---

## 为什么需要分治

### 问题根源

AI 在长上下文中的三大失效模式：

| 问题 | 表现 | 根因 |
|------|------|------|
| **Token 过长** | 上下文窗口溢出，早期指令被截断 | 中间数据全部堆积在对话中 |
| **幻觉加剧** | 长上下文中 AI 开始捏造不存在的信息 | 相关信息被无关信息淹没，检索精度下降 |
| **注意力丢失** | 前文的约束在后文被忽略 | 上下文越长，注意力越分散 |

### 解决思路

将一条长流程拆解为：

```
主线（轻量）: 读取摘要 → 做决策 → 推进下一步
子线（重量）: subagent 执行 → 结果摘要写入 md → 返回
```

核心洞察：**AI 主线不需要看到所有中间数据，只需要看到结构化摘要**。

## 策略 A: Subagent 拆解

### 适用场景

- 可以并行执行的独立分析（如同时审查 3 个模块）
- 需要扫描大量文件（≥5 个文件，每个需要深度分析）
- 子任务有明确的输入/输出契约

### 拆解原则

1. **独立输入/输出**：每个子任务只需要明确的输入参数，产出一份结构化的结果摘要
2. **无循环依赖**：子任务之间不互相依赖（并行前提），或依赖关系清晰（串行前提）
3. **契约化**：每个子任务的 prompt 中明确：目标、作用域、深度、已知信息、输出格式
4. **结果验证**：主线收到子任务结果后，先快速验证合理性再采纳

### 示例：diffscope 风格的 skill 拆解

不拆解的坏设计（所有逻辑在主线）：
```
主线 AI: 读取 diff → 分析模块 A → 分析模块 B → 分析模块 C → 汇总 → 写报告
上下文: [SKILL.md 200行] + [diff数据 500行] + [模块A分析 300行] + [模块B分析 300行] + ...
```
结果：到模块 C 时，AI 已经忘了 SKILL.md 中的全局原则。

拆解后的好设计：
```
Step 1: 主线读取 diff，识别变更涉及的模块
Step 2: 主线拆解为 3 个 subagent：
  - subagent A: 分析模块 A 的变更影响 → 输出: 模块A影响摘要
  - subagent B: 分析模块 B 的变更影响 → 输出: 模块B影响摘要
  - subagent C: 分析模块 C 的变更影响 → 输出: 模块C影响摘要
  （3 个 subagent 并行执行）
Step 3: 主线读取 3 份摘要 → 做全局一致性判断 → 汇总报告
```

每个 subagent 的 prompt 模板：
```
目标: 分析 {模块名} 的代码变更影响
作用域: {模块目录}，只分析此目录下的文件
深度: deep — 追踪符号定义和使用方
已知: 原始 diff 内容、变更类型（重构/修复/新增功能）
输出格式:
  - 变更摘要（3-5 行）
  - 潜在 Bug 列表（编号 + 位置 + 严重度 + 判断依据）
  - 风险提示（编号 + 描述）
  - 无需关注项（为什么认为安全）
```

### 并行约束

- 不并行重复探索同一区域
- 最多 5 个并行 subagent
- 如有 > 5 个子任务，分批执行

## 策略 B: 本地 md 进度追踪

### 适用场景

- 流程固定、步骤多（≥8 步）
- 每步产生大量中间输出
- 需要中断/恢复能力（用户可能在中途离开）
- 需要记录决策过程（为什么跳过、为什么选择某方案）

### progress.md 模板

在 skill 的执行工作目录下创建 `progress.md`：

```markdown

> 状态: 🟢 正常执行 / 🟡 降级执行 / 🔴 阻塞等待 / ⏸️ 暂停
```

### 更新规则

1. **步骤完成时**：勾选 checkbox，记录完成时间
2. **步骤进行中**：更新"当前步骤详情"区
3. **做决策时**：追加"决策记录"表
4. **子任务完成时**：更新"中间结果摘要"
5. **降级发生时**：追加"降级记录"
6. **阻塞时**：更新状态标记，说明阻塞原因和解除条件

### 优势

- AI 可以从 `progress.md` 恢复上下文，不需要重新读取所有中间数据
- 用户可随时查看进度
- 决策可追溯（为什么当时选择了方案 X 而不是 Y）

## 策略 C: 混合（推荐）

### 适用场景

流程最复杂的 skill（如 diffscope 级别的）。

### 工作流

```
主线 AI:
  Step 1: 初始化 progress.md
  Step 2: 执行确定性脚本采集数据
  Step 3: 将结果摘要写入 progress.md
  Step 4: 读取摘要，拆解为 N 个子任务
  Step 5: 并行派发 subagent（每个只拿到自己需要的上下文）
  Step 6: 收集 subagent 结果，验证 → 摘要写入 progress.md
  Step 7: 读取所有摘要 → 全局判断 → 生成最终报告
  Step 8: 自我复核 → 更新 progress.md 最终状态
```

关键：**主线 AI 在每步只看 progress.md 摘要，不直接读取子任务的原始输出**。

## 设计落地清单

在 skill 的 SKILL.md 中，如果启用了复杂流程分治，需明确声明：

### 必须声明项

| 项 | 说明 | 示例 |
|----|------|------|
| 哪些步骤使用 subagent | 标注 subagent 拆解的步骤编号 | "Step 3-5 使用 3 个并行 subagent" |
| progress.md 位置 | 执行时的工作目录 | "在 skill 执行目录下创建 progress.md" |
| progress.md 模板引用 | SKILL.md 中引用模板 | "按照 references/progress-template.md 初始化" |
| 子任务契约 | 每个 subagent 的输入/输出定义 | "subagent 输入: diff 内容 + 模块路径；输出: 影响分析摘要" |
| 主线恢复流程 | 如何从 progress.md 恢复 | "读取 progress.md → 找到当前步骤 → 继续执行" |

### 反模式警示

| 反模式 | 表现 | 危害 |
|--------|------|------|
| **假拆解** | subagent 的 prompt 和主线几乎一样长 | subagent 也面临上下文过长问题 |
| **摘要太粗** | "模块 A 没问题" | 主线无法做全局判断 |
| **摘要太细** | 把 subagent 的完整输出贴进 md | 等同于没拆解 |
| **依赖循环** | subagent A 等 B 结果，B 等 A 结果 | 死锁 |
| **不验证就采纳** | 主线直接使用 subagent 结果不做验证 | 幻觉扩散 |

## 与脚本分离的边界

| 场景 | 用脚本 | 用 subagent | 理由 |
|------|:------:|:-----------:|------|
| 数据采集（git diff、API 拉取） | ✅ | ❌ | 确定性操作 |
| 文件格式转换 | ✅ | ❌ | 确定性操作 |
| 单文件深度分析 | ❌ | ✅ | 需要理解代码意图 |
| 多文件并行分析 | ❌ | ✅ | 上下文拆分 |
| 最终报告生成 | ✅ 或 ❌ | ❌ | 看复杂度——简单用脚本，复杂用 AI |
| 步骤进度追踪 | ❌ | ❌ | 直接写 md，不需要脚本或 subagent |

**判断标准**：能用 if-else 精确描述的 → 脚本；需要理解上下文的 → subagent（如果量大）或主线。

## 案例：diffscope 的混合设计分析

diffscope 是一个典型的混合设计案例：

| diffscope 步骤 | 策略 | 说明 |
|----------------|------|------|
| Step 1-2: 环境检查 + 数据采集 | 脚本 | `get_diff_and_content.py`，确定性操作 |
| Step 3-7: 代码上下文分析 | **应使用 subagent**（当前未用，是改进方向） | 多文件跨模块分析，上下文消耗大 |
| Step 8: 间接影响搜索 | **应使用 subagent** | 需要搜索大量符号使用方 |
| Step 9: QA 分析 | 主线 AI | 需要综合多模块摘要做全局判断 |
| Step 9.5: 自复核 | 主线 AI | 找反证，需要全局视角 |
| Step 10: 报告生成 | 脚本 | `generate_report.py` |

> **教训**：当前 diffscope 在 Step 3-8 中所有分析都在主线 AI 的上下文中进行，这导致上下文窗口快速膨胀。如果按本指南重构，Step 3-8 应在 subagent 中执行，主线 AI 只读取摘要。

## 设计速查

> 以下为原则 9 的核心操作指引，原载于 SKILL.md，现外置于此。

### 何时启用分治

| 场景信号 | 策略 |
|----------|------|
| 需要同时分析 ≥3 个独立模块 | A: Subagent 并行拆解 |
| 主流程超过 8 步 + 每步产生大量输出 | B: progress.md 追踪 |
| 需要扫描 ≥5 个文件/目录且每个需深度分析 | A: Subagent |
| 子任务可独立验证、无循环依赖 | A+B: 混合 |
| 流程固定、只需追踪进度 | B: progress.md |

### progress.md 模板

```markdown
# {skill-name} 执行进度

## 状态: 🟢 进行中 / 🟡 降级执行 / 🔴 阻塞

## 执行清单
- [x] Step 1: 环境检查 ✅
- [x] Step 2: 数据采集 ✅
- [ ] Step 3: 核心分析 ⏳
- [ ] Step 4: 结果复核
- [ ] Step 5: 报告生成

## 决策记录
| 时间 | 步骤 | 决策 | 原因 |
|------|------|------|------|
| ... | ... | ... | ... |

## 中间结果
<!-- 只记录摘要，不记录完整数据 -->
- Step 2 采集到 N 条数据，关键特征: ...
```

### subagent 调用规范

```
task(
  description="简短描述子任务",
  prompt="目标: ... 
作用域: ... 
深度: quick/medium/deep
已知: ...
输出格式: ...",
  subagent_type="explore/general"
)
```

**关键约束**：
- 子任务必须有明确的输入/输出契约
- 子任务结果不可见给用户，必须在主线做摘要
- 不并行重复探索同一区域
- 子任务结果先验证再采纳
