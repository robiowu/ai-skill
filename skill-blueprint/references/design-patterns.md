# 设计模式：8 条核心原则深入解析

> 每条原则包含：原理（为什么重要）、正例（好的设计）、反例（常见错误）、来源追溯。

---

## 原则 1: 步骤分离

### 原理
AI 在长上下文中容易"注意力漂移"——前文的约束在后文被淡忘。将复杂任务拆分为独立步骤，每步有明确的输入、输出、完成标记，让 AI 在每个步骤中只需关注当前步骤的上下文。步骤分离也让人类可以快速定位"当前进行到哪一步"，而不是在一片文字中摸索。

### 正例：diffscope 的 12 步工作流
```
Step 1: 环境检查 ✅
  → 脚本存在？配置可读？
Step 2: 获取工单详情 ✅
  → 读取 yixiezuo 单号信息
...
Step 9.5: Bug/风险自我复核 ✅
  → 对 Step 9 的结论找反证
```
每步有独立的完成标记，步骤间依赖关系清晰（Step 9.5 依赖 Step 9）。

### 反例：模糊流程
```
"首先分析代码，然后检查可能的问题，最后输出报告"
```
没有编号、没有门控、没有输入/输出声明——AI 不知道从哪里开始，用户不知道进行到哪里。

### 来源
diffscope SKILL.md 的工作流进度追踪机制。

## 原则 2: 功能独立（脚本与提示分离）

### 原理
LLM 在处理确定性任务（文件读写、格式转换、API 调用）时不如脚本可靠、可复现、可测试。将确定性逻辑放入脚本，AI 只负责推理判断，两者各司其职。

判断标准：**如果一个操作可以用 if-else 精确描述，它就应该在脚本里；如果需要权衡判断，它应该在 AI 提示词里。**

### 正例：diffscope 的脚本设计
```
scripts/get_diff_and_content.py  → 确定性：拉取 diff 数据
scripts/generate_report.py       → 确定性：HTML 渲染
SKILL.md Step 9                  → 推理：QA 分析判断
SKILL.md Step 9.5                → 推理：自我复核
```

### 反例：提示词中内嵌代码
```markdown
请执行以下 Python 代码拉取数据：
```python
import requests
def get_data():
    resp = requests.get(url, params={...})
    ...
```
```
代码在提示词中无法独立测试，参数变化时需要 AI 重写整个代码块。

### 来源
skill-creator 的 Anatomy of a Skill（scripts/ 目录定义）。

## 原则 3: 一致性校验

### 原理
AI 的推理可能产生幻觉——从正确的输入推导出错误的结论。在输出步骤后增加一个"找反证"的复核步骤，可以有效减少幻觉累积。关键不是"再检查一遍"，而是**主动搜索能推翻前一步结论的证据**。

### 正例：diffscope Step 9.5 复核机制
```
Step 9:  输出 Bug/风险初稿（正证："这里有问题"）
Step 9.5: 逐条找反证（"该问题已被处理了吗？"）
  - 搜索符号定义处、调用方保护逻辑、配置/协议同步
  - 找到反证 → 降级/移除
  - 未找到 → 维持/升级
  - 复核日志可见
```

### 反例：自我复查但不找反证
```markdown
最后请重新检查你的分析是否正确
```
没有具体方向，AI 倾向于再次确认自己已有的结论（确认偏误）。

### 来源
diffscope Step 9.5 的"主动找反证，而非再找正证"设计。

## 原则 4: 过程可量化

### 原理
"好"和"不好"是主观判断，无法指导改进方向。可量化的评分让设计者知道差距在哪、改进后是否有提升。

### 正例：skill-checker 的评分体系
```
起始 10 分
Error: -2 分
Warning: -0.5 分
底线 1 分
定性调整: ±1 分

分数段：8-10 生产就绪 / 5-7 可用但需改进 / 1-4 需大幅修改
```
机械公式确保不同审查者得到相似分，定性调整保留对"精妙设计"或"全面混乱"的判断空间。

### 反例：纯定性评价
```markdown
这个 skill 设计还不错，但有些地方需要改进
```
无法量化"还不错"的程度，无法追踪改进效果。

### 来源
skill-checker 的 Scoring rubric。

## 原则 5: 评估规则化

### 原理
审查者不应凭直觉判断，而应有一个可操作的检查清单。每项检查应该能客观回答"是/否"，而不是"好不好"。

### 正例：skill-checker 的 5 维度检查清单
```
维度 1: 结构合规性
  1.1 SKILL.md 是否存在且非空？   → 可客观判定
  1.2 frontmatter 是否包含 name？  → 可客观判定
  1.3 frontmatter 是否包含 description？ → 可客观判定
```

### 反例：不可操作的检查项
```
- 代码是否优雅？
- 设计是否合理？
```
没有判断标准，不同审查者答案不同。

### 来源
skill-checker 的 Per-Dimension Checklist Evaluation。

## 原则 6: 降级必有路

### 原理
Skill 的执行环境不可控——外部 API 可能宕机、MCP 服务可能未部署、文件可能不存在。如果设计时假设一切正常，运行时一个依赖缺失就会导致流程卡死。

### 正例：diffscope 的降级策略
```
依赖               降级行为                         标注
─────────────────────────────────────────────────────────
local-code-mcp     Step 8 跳过                      报告中注明限制
branch_switch_url  使用 master 分支搜索              报告中注明
redmine token      功能目标基于代码反推              报告中注明
report_upload_url  仅保存本地                        提供本地路径
```
每个依赖都有明确的降级行为，降级后在输出中有 `⚠️ 分析限制` 标注。

### 反例：无降级的依赖声明
```markdown
需要 local-code-mcp 服务才能执行分析
```
如果服务不可用，整个 skill 无法执行，用户不知道该怎么办。

### 来源
diffscope 全局执行原则第 4 条："工具不可用时必须降级"。

## 原则 7: 知识案例化

### 原理
每次执行 skill 时积累的经验如果不做结构化沉淀，就会在下次执行时丢失。将经验转化为"触发模式 + 检查规则"的案例，让 AI 在遇到相似场景时自动激活相关检查。

### 正例：diffscope 案例库
```
CASE-001: 缓存键维度不匹配
  触发模式：diff 中出现 Cache/cache/CacheKey → 自动激活
  检查规则：找到 CacheKey 生成逻辑和查询条件 → 对比维度 → 维度不完整= Bug

CASE-002: Type Discriminator 失效
  触发模式：in-place 字段写入 + init/preprocess 函数 → 自动激活
  检查规则：搜索字段读取方（跳过模式 + 写入模式） → 确认是否破坏隐式假设

CASE-003: 条件变更未验证数据约束
  触发模式：not Cfg.X → 其他条件 → 自动激活
  检查规则：追溯原条件意图 → 验证数据配置约束 → 检查预处理是否破坏意图
```

### 反例：不可复用的经验
```markdown
上次分析 #12345 时发现了一个缓存问题，注意检查
```
没有结构化，"缓存问题"太笼统，下次 AI 不知道什么时候该检查、怎么检查。

### 来源
diffscope 的 cases/ 案例库和 case-matching.md 机制。

## 原则 8: 反模式自检

### 原理
AI 在某些场景下会反复犯同样的错误——例如根据 diff 猜测影响方向而不验证数据约束、看到条件变更就直接判断"原来不该通过的现在通过了"。将这些已知错误模式记录下来，执行中主动对照检查。

### 正例：diffscope 反模式速查表
```
反模式 1: "子对象也会错误通过"
  触发：看到 not X → 其他条件
  纠偏：先验证"谁会配置 X"的数据约束 → 再判断影响方向

反模式 3: 升级为 Bug（证据不足）
  触发：仅凭推理判断为 Bug
  纠偏：执行 Step 9 问题分级标准 → 未经验证只能列为风险或注意事项
```

### 反例：没有反模式机制的 skill
```markdown
分析时请注意准确性
```
没有具体指引，AI 不知道该注意什么。

### 来源
diffscope 的反模式速查表（anti-patterns）和 CASE-003 的教训。

## 原则 9: 复杂流程分治

### 原理
当 skill 涉及大批量操作（≥5 个步骤且每步产生大量中间数据）、强流程依赖、且不适合纯脚本固化时，将所有逻辑堆在主线 AI 的上下文中会导致三个问题：token 窗口溢出（早期指令被截断）、幻觉加剧（相关信息被无关信息淹没）、注意力丢失（前文约束在后文被忽略）。

解决思路：将长流程拆解为轻量主线 + 重量子线。主线只需读取结构化摘要做决策，不直接接触所有中间数据。

### 正例：subagent + progress.md 混合设计
```
策略 A: Subagent 拆解
  Step 3-5: 3 个并行 subagent 分别分析模块 A/B/C
  每个 subagent 输出: 变更摘要 + Bug 列表 + 风险提示

策略 B: progress.md 追踪
  执行目录下维护 progress.md:
    - [x] Step 1 完成
    - [ ] Step 2 进行中
    - 决策记录: D1: 跳过 MCP 检查（目标环境无 MCP）
    - 中间结果摘要（非完整数据）

策略 C: 混合
  subagent 执行 → 结果摘要写入 progress.md → 主线读取摘要继续
```

### 反例：所有逻辑堆在主线
```
主线 AI:
  Step 1: 读取 diff（500行）
  Step 2: 分析模块 A（300行输出）
  Step 3: 分析模块 B（300行输出）
  Step 4: 分析模块 C（300行输出）
  Step 5: 汇总 → 此时 AI 已忘记 SKILL.md 中的全局原则
```

### 判断标准
- 能用 if-else 精确描述的 → 脚本
- 需要理解上下文 + 量小（≤2 个文件） → 主线 AI
- 需要理解上下文 + 量大（≥3 个文件或模块） → subagent
- 需要中断/恢复能力 + 多步骤 → progress.md

### 来源
diffscope 的上下文膨胀经验教训提炼，以及对 AI 长上下文注意力衰减的工程应对。
