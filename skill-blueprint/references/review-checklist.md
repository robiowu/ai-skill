# Skill 评估检查清单

> Stage 3 整体评估的完整检查清单和评分细则。

---

## 评估前置：Skill 定位

> 参考：skill-checker L22-32

在开始 6 维度审查之前，必须先完成 skill 定位和确认。

### 定位流程

1. 如果用户提供 skill **名称**（如"审查一下 my-skill"），按以下顺序搜索：
   - `~/.codemaker/skills/{name}/SKILL.md`（用户级）
   - `skills/{name}/SKILL.md`（项目相对路径）
   - 如均未找到 → 请用户提供完整路径

2. 如果用户提供 **路径**，直接读取该路径下的 SKILL.md

3. 读取 SKILL.md 和完整目录树

### 确认信息

定位后输出简短确认信息，等待用户确认：

```
目标 skill: `my-skill`
- SKILL.md: 320 行
- 目录结构: references/ (3 文件), scripts/ (2 文件), cases/ (5 文件)
- 类型: Generator

开始审查？(输入"直接审"跳过确认)
```

如 SKILL.md 不存在 → 报告错误并终止。

## 维度 1: 结构审查（6 项）

| # | 检查项 | 判断标准 | 严重度 |
|---|--------|----------|:------:|
| 1.1 | SKILL.md 是否存在且非空 | 文件存在且内容 > 0 字节 | Error |
| 1.2 | frontmatter 是否包含 name | `name:` 字段存在且非空 | Error |
| 1.3 | frontmatter 是否包含 description | `description:` 字段存在且非空 | Error |
| 1.4 | description 是否有效 | 非空、非模板占位符（如"待补充"）、含触发关键词、20-200 字 | Warning |
| 1.5 | 是否包含执行流程 | 有编号的 Phase/Step 划分 | Warning |
| 1.6 | 是否有参考文件索引 | 有指向 references/ scripts/ cases/ 的索引表 | Warning |

## 评分规则

### 机械评分

- 起始: **10 分**
- 每项 Error: **-2 分**
- 每项 Warning: **-0.5 分**
- Info 项: 不扣分
- N/A 项: 不计入分母
- 底线: **1 分**

### 定性调整

在机械分基础上 ±1 分：
- **+1**: 设计特别精妙、文档特别完整、有独特的创新点
- **-1**: 整体混乱、多处不一致、有根本性设计缺陷未被检查项覆盖

### 分数段含义

| 分数 | 评价 | 建议 |
|:----:|------|------|
| 8-10 | 🟢 生产就绪 | 可以直接使用 |
| 5-7 | 🟡 可用但需改进 | 建议修复 Warning 项后使用 |
| 1-4 | 🔴 需大幅修改 | 存在阻塞性 Error，不建议直接使用 |

---

## 严重度定义

| 级别 | 标记 | 含义 | 典型场景 |
|------|:----:|------|----------|
| Error | 🔴 | 阻塞性问题，必须修复 | 缺少 name、硬编码密钥、无降级路径 |
| Warning | 🟡 | 偏离最佳实践，建议修复 | SKILL.md 过长、描述不准确 |
| Info | 🔵 | 优化建议，锦上添花 | 缺少 README、可增加索引 |

## 关键陷阱（Gotchas）

> 参考：skill-checker L118-124

评估过程中需主动规避以下常见陷阱，避免给出虚假高分或错误判断。

### （一）N/A 项必须显式标记，不能静默跳过

每个不适用（N/A）的检查项必须在表中显式标记 ➖，并附简短备注：

```
| 2.3 | scripts/ 是否有 requirements.txt | ➖ | 纯对话型 skill，无 scripts/ |
```

**错误做法**：直接省略 N/A 行，或标记为 ✅ 假装通过。

### （二）严格遵循扣分公式，不虚高、不虚低

评分必须严格按机械公式计算，不可因"总体感觉还不错"而手动加分，也不可因"这个 skill 太小"而放宽标准。

- Error = -2，不可因"这个 Error 不太严重"而改为 -1
- Warning = -0.5，不可因"3 个 Warning 凑在一起"而改为 -2
- 定性调整上限 ±1，不可超出

### （三）验证文件存在时必须实际检查

涉及文件存在的检查项（如"references/ 中的文件是否被引用"、"引用文件是否存在"），必须调用文件工具实际检查，不可凭猜测或推断。

**常见错误**：SKILL.md 提到 "见 `references/checklist.md`"，评估者凭经验认为"应该存在"而标记 ✅，实际文件不存在。

### （四）≤30 行极简 skill 的过度工程化处理

对极其简单的 skill（≤30 行，如纯 Tool Wrapper），涉及拆分、外置、复杂性的检查项应标记为 N/A：

| 检查项 | 极简 skill 处理 |
|--------|----------------|
| SKILL.md 是否过长 | N/A（本来就很短） |
| 是否内嵌大段代码 | N/A（极简 skill 本身可能就是一段代码，内嵌合理） |
| 是否有参考文件索引 | N/A（极简 skill 不需要 resources） |
| 步骤间输入/输出是否声明 | 按实际判断（简单的步骤仍需声明） |

**核心原则**：过度工程化比简单更糟。强迫一个 25 行的 skill 做 Domain organization 拆分是浪费。

### （五）机械评分后必须附加定性说明

机械公式覆盖所有检查项，但不能覆盖"整体设计思想"。0 Error + 0 Warning = 10 分的 skill 可能存在检查项未覆盖的根本性缺陷（如 AI 和脚本的职责边界完全倒置）。

此时：
- 定性调整 **不扣分**（Gotchas 不改变分数本身）
- 在总评中明确说明："虽然机械评分 10 分，但存在以下设计隐患：<具体问题>。建议关注。"
- 此说明作为评估者的专业判断补充，供 skill 设计者参考
