# Proposal: skill-blueprint — Skill 设计范式与最佳实践元 Skill

## 概述

创建一个**元 Skill（meta-skill）**，名为 `skill-blueprint`，用于指导后续所有 skill 型项目的规范化生成。它从已有的高质量 skill 设计实践中提取通用范式、最佳实践和质量标准，为 AI 辅助生成 skill 提供结构化的设计约束和验证规则。

## 动机与背景

### 现状问题

经过对 `skill-creator`、`skill-checker`、`diffscope` 等成熟 skill 的深度分析，发现当前 skill 设计存在以下普遍问题：

1. **质量参差不齐**：缺少统一的规范化标准，skill 之间的结构、内容深度、可测试性差异巨大
2. **脚本与提示耦合**：大量 skill 将确定性逻辑混入提示词，导致不可测试、不可复用
3. **缺乏自校验机制**：输出型 skill 没有前后一致性验证，结果质量依赖 AI 单次推理
4. **降级路径缺失**：依赖不可用时无 fallback，执行流程卡死
5. **知识无法沉淀**：分析经验无法案例化积累，每次从零开始
6. **过度冗余**：提示词堆砌大量 MUST/ALWAYS，缺乏原理阐释，模型理解不深

### 已有基础

本 skill 的设计范式提取自以下四个源头：

| 源头 | 提取的范式 |
|------|-----------|
| **skill-creator**（官方创建 skill） | 渐进式加载、核心循环、可量化评估、描述优化 |
| **skill-checker**（官方审查 skill） | 5 维度检查清单、严重度分级、评分机制、设计模式识别 |
| **diffscope**（实战 QA 分析 skill） | 12 步工作流门控、降级处理、案例库驱动、反模式速查、自我复核、时间盒约束、输出裁剪 |
| **diffscope 案例库**（CASE-001/002/003） | 触发模式匹配、可操作检查规则、组合触发优先级 |

## 目标

### 核心能力

1. **设计审查**：当用户描述一个 skill 想法时，自动应用范式检查——结构是否合理、步骤是否分离、是否有降级路径
2. **模板生成**：根据 skill 类型（Generator / Reviewer / Pipeline / Tool Wrapper）推荐对应的目录结构和工作流模板
3. **质量评分**：对已有 skill 按 5 维度评分，输出改进建议
4. **案例驱动**：指导如何将执行经验转化为可复用的案例知识

### 非目标

- 不替代 `skill-creator`——skill-blueprint 提供**设计范式指导**，skill-creator 提供**创建和迭代工具链**
- 不替代 `skill-checker`——skill-blueprint 的审查偏**设计层面**（架构、范式），skill-checker 偏**执行层面**（格式、安全、完整性）
- 不强制执行单一范式——提供多种模式语言，供用户按场景选择

### 完整生命周期与分工模型

skill-blueprint 不是孤立的——它位于 skill 研发流水线的**设计阶段**，向上承接需求，向下衔接实现和审查：

```
                    用户需求
                       │
                       ▼
┌──────────────────────────────────────────────────────────┐
│  ① 设计阶段 → skill-blueprint（本 skill）                  │
│     • 分析 skill 类型（Generator / Reviewer / Pipeline...）│
│     • 推荐目录结构和工作流模板                               │
│     • 检查是否满足 8 条核心原则                              │
│     • 输出设计蓝图 → "设计已就绪，可进入实现阶段"             │
└────────────────────────┬─────────────────────────────────┘
                         │ 输出：设计蓝图
                         ▼
┌──────────────────────────────────────────────────────────┐
│  ② 实现阶段 → skill-creator                               │
│     • 按蓝图编写 SKILL.md                                  │
│     • 创建测试用例 + 运行基准                               │
│     • 迭代改进 + 描述优化                                   │
│     • 打包输出 .skill 文件                                 │
└────────────────────────┬─────────────────────────────────┘
                         │ 输出：可安装的 skill 包
                         ▼
┌──────────────────────────────────────────────────────────┐
│  ③ 审查阶段 → skill-checker                               │
│     • 5 维度执行层面审查（结构/内容/目录/可测试性/安全）       │
│     • 严重度分级 + 评分                                     │
│     • 输出审查报告和改进建议                                 │
└──────────────────────────────────────────────────────────┘
```

**skill-blueprint 的分内之事**：确保 skill 的**架构设计**合理——步骤是否分离、依赖是否有降级路径、输出是否有自校验、知识是否可案例化。

**skill-blueprint 不分内之事**：编写具体代码、运行测试基准、打包安装文件——这些交给 skill-creator。当设计蓝图完成后，skill-blueprint 应主动引导用户："设计已就绪，建议使用 `skill-creator` 进入实现阶段。"

## 设计概要

### 核心设计原则（从四个源头提取）

```
┌─────────────────────────────────────────────────────┐
│                 skill-blueprint 核心原则               │
├─────────────────────────────────────────────────────┤
│ 1. 步骤分离     每步独立验证，有明确输入/输出/完成标记   │
│ 2. 功能独立     脚本处理确定性任务，AI 处理推理判断      │
│ 3. 一致性校验   输出步骤必须配复核步骤，防幻觉累积        │
│ 4. 过程可量化   断言 + 评分 + 基准，为改进提供方向        │
│ 5. 评估规则化   检查清单可操作，严重度可分级             │
│ 6. 降级必有路   每个外部依赖定义 fallback 路径          │
│ 7. 知识案例化   执行经验沉淀为触发模式 + 检查规则         │
│ 8. 反模式自检   执行中对照反模式表，主动纠偏             │
└─────────────────────────────────────────────────────┘
```

### 目录结构范式

```
skill-name/
├── SKILL.md                   # AI 执行指令（唯一的提示词入口）
│   ├── YAML frontmatter       # name + description（触发机制）
│   └── Markdown 指令          # 工作流 + 原则 + 约束
├── README.md                  # 人类可读文档
├── cases/                     # 案例库（可选，知识密集 skill 推荐）
│   ├── README.md              # 案例规范
│   └── CASE-XXX-*.md          # 统一模板的案例文件
├── scripts/                   # 确定性脚本（与提示词分离）
│   ├── requirements.txt       # Python 依赖
│   └── *.py                   # 可独立测试的脚本
├── references/                # 参考资料（可选，大型 skill 推荐）
│   └── *.md                   # 领域知识、检查清单
└── assets/                    # 静态资源（可选）
    └── *.html / *.css / *.json
```

### 触发策略

当用户使用以下触发词时激活：
- "设计一个 skill"、"创建 skill"、"skill 架构"
- "skill 最佳实践"、"skill 规范"、"skill 范式"
- "审查 skill 设计"、"skill 设计是否合理"
- "帮我规范化这个 skill"

### 与现有 skill 的边界

| 维度 | skill-blueprint | skill-creator | skill-checker |
|------|:--:|:--:|:--:|
| **阶段** | 设计 | 实现 | 审查 |
| **关注点** | 架构是否合理 | 能否正确执行 | 格式是否合规 |
| **核心动作** | 审查设计、推荐模板 | 编写、测试、迭代、打包 | 5 维度评分 |
| **输出** | 设计蓝图 + 改进建议 | .skill 安装包 | 审查报告 |
| **审的是什么** | 设计决策 | 执行效果 | 最终成品 |

## 交付物

1. **SKILL.md**：核心指令，包含设计范式库、skill 类型模板、评估清单
2. **references/design-patterns.md**：详细的设计模式语言
3. **references/skill-types.md**：按类型分类的模板（Generator / Reviewer / Pipeline / Tool Wrapper / Case-Driven）
4. **references/checklist-design.md**：设计层面审查清单
5. **references/anti-patterns.md**：skill 设计反模式汇总

## 风险与约束

- 范式可能过拟合——需定期从新 skill 中反向更新范式库
- 过度约束可能抑制创新——需保持"推荐而非强制"的基调
- 与 skill-creator/skill-checker 的边界可能模糊——需在描述中明确分工
