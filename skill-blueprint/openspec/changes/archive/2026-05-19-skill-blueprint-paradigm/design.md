# Design: skill-blueprint — 架构与规则详解

## 1. 架构总览

skill-blueprint 本身采用 **Reviewer + Template** 混合模式：

```
用户输入（skill 想法 / 已有 skill）
        │
        ▼
┌───────────────────────────────────┐
│  Phase 1: 类型识别                  │
│  分析 skill 意图 → 匹配类型模板       │
└───────────────┬───────────────────┤
                ▼
┌───────────────────────────────────┐
│  Phase 2: 范式审查                  │
│  按 8 条原则逐条检查，标记通过/偏离     │
└───────────────┬───────────────────┤
                ▼
┌───────────────────────────────────┐
│  Phase 3: 设计评分                  │
│  5 维度评分 + 严重度分级              │
└───────────────┬───────────────────┤
                ▼
┌───────────────────────────────────┐
│  Phase 4: 改进建议                  │
│  Top-N 建议 + 引导进入 skill-creator │
└───────────────────────────────────┘
```

每个 Phase 有明确输入/输出和完成标记（✅），遵循自身倡导的"步骤分离"原则。

## 2. Skill 类型模板

### 2.1 Generator（生成器型）

**识别特征**：输入数据/文件 → 经过处理 → 输出新文件/报告

**典型案例**：diffscope（diff 数据 → QA 分析报告）

**推荐模式**：
```
Phase A: 数据采集（脚本）
    ↓
Phase B: 数据分析（AI 推理）
    ↓
Phase C: 结果校验（AI 自检）
    ↓
Phase D: 文件生成（脚本）
```

**强制要求**：
- 数据采集和文件生成必须用脚本（确定性，可独立测试）
- Phase C（结果校验）不可省略——输出型 skill 必须有前后一致性验证
- 校验日志必须可见，不能静默修正

### 2.2 Reviewer（审查器型）

**识别特征**：输入制品 + 规则 → 逐条检查 → 输出审查报告

**典型案例**：skill-checker（skill 文件 + 检查清单 → 审查报告）

**推荐模式**：
```
Phase A: 读取制品 + 加载检查清单（references/）
    ↓
Phase B: 逐维度评估（AI 推理 + 脚本辅助）
    ↓
Phase C: 汇总评分 + Top-N 建议
```

**强制要求**：
- 检查清单必须存放在 `references/`，不在 SKILL.md 中内联
- 每项检查必须输出通过/未通过/不适用，不能跳过
- 评分机制必须可复现（机械公式 + 定性判断各占权重）

### 2.3 Pipeline（流水线型）

**识别特征**：多阶段串行执行，阶段间有数据依赖

**典型案例**：diffscope（Step 1→2→...→12 串行工作流）

**推荐模式**：
```
Step 1: 准备 → Step 2: 获取 → Step 3: 处理 → ... → Step N: 清理
   ✅/⏭️         ✅/⏭️         ✅/⏭️              ✅/⏭️
```

**强制要求**：
- 每一步有明确的门控标记（✅ 完成 / ⏭️ 跳过 / ❌ 失败）
- 依赖不可用时必须降级，不得卡死
- 时间盒约束：每步声明最大执行时间
- 阶段间输出格式规约化（json schema 或明确的字段约定）

### 2.4 Tool Wrapper（工具封装型）

**识别特征**：封装外部工具/MCP 的调用，附加参数校验和错误处理

**典型案例**：将 git diff 封装为结构化分析入口

**推荐模式**：
```
参数校验 → 调用外部工具 → 结果结构化 → 错误处理/降级
```

**强制要求**：
- 工具不可用时的降级行为必须显式定义
- 参数 schema 必须在 SKILL.md 中声明
- 外部工具调用必须集中管理（一个脚本/一个函数），不分散到多处

### 2.5 Case-Driven（案例驱动型）

**识别特征**：知识密集型，通过历史案例匹配来增强分析准确性

**典型案例**：diffscope 案例库（CASE-001/002/003）

**推荐模式**：
```
当前场景 → 特征提取 → 案例匹配（trigger_patterns） → 激活检查规则 → 执行检查
```

**强制要求**：
- 案例文件必须有统一模板（见 `cases/README.md`）
- 触发模式（trigger_patterns）必须可机械匹配，不能依赖语义理解
- 检查规则必须可操作（找到 X → 比对 Y → 判断 Z），不能是笼统建议
- 案例必须去项目化（去除具体变量名/路径，保留通用模式）

## 3. 八条核心原则的应用规则

### 原则 1: 步骤分离

**含义**：每个步骤有明确的输入、输出、完成标记，可独立验证。

**审查标准**：
- [ ] 每个步骤有编号和名称
- [ ] 步骤间输入/输出格式在文档中声明（可简写）
- [ ] 每个步骤有完成标记（✅/⏭️ 或等效机制）
- [ ] 步骤粒度适中——不是"做分析"一个步骤，也不是"打开文件"就算一步

**偏离判定**：
- 步骤全部堆在一段文字中 → **Warning**
- 步骤有标号但无完成标记 → **Warning**
- 完全没有步骤划分 → **Error**

### 原则 2: 功能独立（脚本与提示分离）

**含义**：确定性任务交给脚本，推理判断交给 AI。

**审查标准**：
- [ ] 文件读写、格式转换、数据拉取使用脚本
- [ ] 脚本可独立运行和测试（有明确的 CLI 参数）
- [ ] SKILL.md 中不内嵌大段代码（单行命令除外）
- [ ] 脚本有 `requirements.txt` 声明依赖

**偏离判定**：
- 确定性逻辑写在 SKILL.md 中（如大段 Python 代码） → **Warning**
- 有脚本但无依赖声明 → **Info**
- 脚本与 SKILL.md 中的参数不一致 → **Error**

### 原则 3: 一致性校验

**含义**：输出型步骤必须有复核步骤，防止 AI 幻觉累积。

**审查标准**：
- [ ] Generator 型 skill 的输出步骤后是否跟随了校验步骤
- [ ] 校验步骤有"找反证"导向（不是再找正证）
- [ ] 校验结果可见（日志或标记），非静默修正
- [ ] 校验发现的问题有明确的处置规则（维持/升级/降级/移除）

**偏离判定**：
- 输出步骤无校验 → **Error**（Generator 型）
- 有校验但只找正证 → **Warning**
- 校验结果不可见 → **Warning**

### 原则 4: 过程可量化

**含义**：通过断言、评分、基准，为 skill 改进提供方向而非主观感觉。

**审查标准**：
- [ ] Reviewer 型 skill 有评分公式
- [ ] 评分公式可复现（其他 AI 跑同一个 skill 应得相似分）
- [ ] 评分有分级解释（如 8-10=就绪 / 5-7=可用 / 1-4=需大幅修改）
- [ ] Generator 型 skill 预留了与 skill-creator 的测试基准对接

**偏离判定**：
- Reviewer 型无评分 → **Error**
- 有评分但无分级解释 → **Warning**
- Generator 型完全无量化考量 → **Info**

### 原则 5: 评估规则化

**含义**：检查清单必须可操作，严重度可分级。

**审查标准**：
- [ ] 检查清单有统一格式（编号 + 检查项 + 判断标准）
- [ ] 检查项可客观判定（不是"写得好不好"这种主观题）
- [ ] 严重度有明确分级（Error / Warning / Info）
- [ ] N/A 项被显式标记而非跳过

**偏离判定**：
- 检查项全是主观判断 → **Warning**
- 无严重度分级 → **Warning**
- 无检查清单（Reviwer 型） → **Error**

### 原则 6: 降级必有路

**含义**：每个外部依赖定义 fallback 路径，执行不卡死。

**审查标准**：
- [ ] 每个外部工具/MCP 依赖有降级声明
- [ ] 降级行为有明确边界（跳过什么、保留什么）
- [ ] 降级后在输出中有标注（如 "⚠️ 分析限制"）
- [ ] 降级不导致静默遗漏关键步骤

**偏离判定**：
- 有外部依赖但无降级声明 → **Error**
- 降级声明太笼统（如"跳过此步骤"而无具体行为） → **Warning**
- 无外部依赖 → **N/A**

### 原则 7: 知识案例化

**含义**：执行经验沉淀为可匹配、可复用的案例知识。

**审查标准**：
- [ ] 案例文件有统一模板（元信息 + 触发模式 + 模式描述 + 检查规则 + 关联知识）
- [ ] 触发模式可机械匹配（关键词/正则/结构模式）
- [ ] 检查规则可操作（不是"注意 xxx"而是"找到 X → 比对 Y → 判断 Z"）
- [ ] 案例去项目化（去除特定变量名、路径、工单号等）

**偏离判定**：
- 案例缺少触发模式 → **Error**
- 触发模式太抽象无法匹配 → **Warning**
- 检查规则不可操作 → **Warning**

### 原则 8: 反模式自检

**含义**：执行中对照已知反模式表，主动纠偏。

**审查标准**：
- [ ] 有反模式汇总（外部化到 `references/anti-patterns.md` 或在 SKILL.md 中）
- [ ] 反模式有触发条件和纠偏指引
- [ ] 纠偏指引可操作（不是"注意不要这样做"而是"如果发现 X，应改为 Y，因为 Z"）

**偏离判定**：
- 无反模式机制 → **Info**（非必须，但有则加分）
- 有反模式但无可操作纠偏 → **Warning**

## 4. 设计评分体系

输出格式（参考 skill-checker，适配设计层面）：

```
## 设计审查报告: {skill-name}

### 类型识别
- 类型: [Generator / Reviewer / Pipeline / Tool Wrapper / Case-Driven / Hybrid]
- 匹配度: [高 / 中 / 低]（偏离类型模板的程度）

### 维度 1: 结构合规性 (X/4 通过)
每项评估一项结构原则（步骤分离、门控标记、步骤粒度、输入/输出声明）

### 维度 2: 脚本分离度 (X/3 通过)
确定性任务是否脚本化、脚本是否独立可测、是否有依赖声明

### 维度 3: 自校验机制 (X/3 通过)
是否有复核步骤、复核是否"找反证"导向、校验结果是否可见

### 维度 4: 降级健壮性 (X/3 通过)
外部依赖是否有降级声明、降级行为是否明确、降级是否标注

### 维度 5: 知识可沉淀性 (X/3 通过)
是否有案例机制、触发模式是否可匹配、检查规则是否可操作

---

### 发现汇总

#### 🔴 设计缺陷（必须修复）
#### 🟡 设计偏离（建议修复）
#### 🔵 设计优化（可以改进）

---

### 总评
- 设计评分: X/10 — {理由}
- 推荐类型: {最匹配的类型模板}
- Top 3 设计改进建议
```

**评分规则**：
- 起始 10 分
- 设计缺陷（Error）：-2 分
- 设计偏离（Warning）：-0.5 分
- 设计优化（Info）：不扣分
- 底线 1 分
- 定性调整：±1 分（设计特别精妙/特别混乱时）

## 5. 交付物文件规划

```
skill-blueprint/
├── SKILL.md                         # 核心指令
│   └── 内容：Phase 1-4 工作流 + 类型模板速查 + 8 原则应用指引
├── references/
│   ├── skill-types.md               # 5 种类型模板的详细说明和示例
│   ├── design-patterns.md           # 8 条原则的深入解析 + 正反例
│   ├── checklist-design.md          # 设计审查检查清单（可操作细则）
│   └── anti-patterns.md             # 常见设计反模式 + 纠偏指引
└── README.md                        # 人类可读文档
```

**设计决策**：
- skill-blueprint 本身不包含 `scripts/`——它是纯审查/指导型，不产生文件输出
- 不包含 `cases/`——它的知识不来自案例匹配，而是来自模式语言本身
- SKILL.md 保持轻量（<300 行），详细内容都放到 `references/`

---

## 6. 与 skill-creator 的交接约定

skill-blueprint 的设计阶段结束后，输出应包含以下信息供 skill-creator 使用：

1. **推荐类型**：Generator / Reviewer / Pipeline / Tool Wrapper / Case-Driven
2. **推荐目录结构**：需要哪些目录（scripts/、cases/、references/ 等）
3. **关键约束**：哪些步骤必须脚本化、哪些步骤必须有校验
4. **风险提示**：设计中的已知风险点（如依赖的降级策略是否充分）
5. **测试建议**：哪些行为应该被测试覆盖（为 skill-creator 的 evals 提供方向）
